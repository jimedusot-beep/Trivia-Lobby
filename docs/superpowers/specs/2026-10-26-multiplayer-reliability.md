# Multiplayer reliability

The owner authorized implementing the six reliability recommendations from the source research. Preserve every existing game, account/private-deck authorization, QR entry and public guest flow. Keep the existing free Render/Neon services; do not provision or upgrade resources. This changes our own implementation, without importing reference-project code or assets.

Live room recovery must use private, server-owned PostgreSQL checkpoints. Save accepted state changes before delivering credentials, success acknowledgments, scores or snapshots. Save only credential hashes, never raw reconnect tokens or sockets. Scope checkpoints by transport and room code, use optimistic versions to fence stale writers, expire inactive rooms after ten minutes, cap each serialized checkpoint at 4 MiB and the total active checkpoint payload at 32 MiB. A failed write must not acknowledge an uncommitted action. Restore clocks/deadlines and nested Maps/Sets; apply an elapsed deadline once without re-scoring a revealed round. All restored connections begin offline.

Retain per-room serialization, actor/role authorization, server-owned scores, private role projections and match/phase validation. Quiz commands gain optional correlated request IDs and original-result replay for compatibility with existing clients. Reusing an ID for another command rejects. New browser clients send IDs and phase/match identity. Duplicate commands never apply points, purchases, bonuses or host advancement twice.

Both transports detect stale connections and bound slow clients. Browser reconnects use exponential backoff with jitter, recover on foreground/online, retain credentials during transient outages, and show connected only after room resume and a fresh authoritative snapshot. Fatal/replaced sessions stop retrying. Deadlines remain server-controlled.

Acceptance includes real loopback WebSocket tests with 20 players sharing one source IP, burst submissions, duplicate requests, simultaneous reconnects, host loss, old-socket close races, private-payload checks, process replacement using the same store, expired deadlines, failed writes and stale checkpoint writers. Run the existing app/party suites, type checks, production build and appropriate PostgreSQL/browser checks. Actual 20-phone acceptance is still a manual test, not something synthetic tests can claim.
